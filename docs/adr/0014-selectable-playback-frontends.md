# ADR-0014：播放端支持可选 Chrome 与 mpv 前端

- 状态：已接受，待实现
- 日期：2026-11-01

## WHY

现有电视播放端使用 Chromium kiosk：HTML 同时承担待机、首次设置、频道菜单和 `<video>` 播放。这让早期实现、调试和遥控器交互很简单，但 Chromium 的容器、视频编码和音频编码支持比家庭存量片库窄。NAS 映射盘中的 MKV、TS、HEVC、DTS 等文件可被本地播放器直接解码，却会迫使现有方案生成完整 H.264/AAC 兼容缓存。在性能较弱的电视电脑上，软件转码很慢，也浪费 CPU、磁盘与 NAS 带宽。

网站节目已由 yt-dlp 下载为本地缓存；本地片库也已是可信的本机或映射盘文件。因此电视端可把这两类条目统一解析为可播放文件，不必强制通过浏览器解码。同时，Chrome 前端的成熟设置页、菜单和调试价值不应被一次性丢弃。

## WHAT

将“频道与播出核心”和“电视播放前端”分离，支持同一套状态机下可选的播放前端：

- `chrome`：保留当前 kiosk Chrome/Edge、`/tv` HTML、HTTP Range 媒体流和电视 WebSocket，并作为旧部署的默认选择。
- `mpv`：Showrunner 托管唯一的全屏 mpv 进程，通过 Windows named pipe 上的 JSON IPC 加载文件、控制播放并接收进度、结束和异常事件。本地/NAS 节目直接读原路径；网站节目等缓存就绪后读缓存文件。
- `auto` 保留为后续选项；在降级规则、状态告警和测试完整前不做静默自动切换。

此处的“播放前端”仅指电视上输出画面和接受本地遥控器按键的实现，不是手机遥控器 Web 界面。手机遥控器、频道、合集、时刻表、播放上限、日志和异常跳过保持为共享核心。

`playerFrontend`、`mpvPath`、`chromePath`、屏幕编号等是机器特定配置，保存在同级数据目录的 `config.json`，不进入可提交分享的频道/合集资产。旧安装缺少该字段时继续选择 `chrome`，保证升级不改变现有播放行为。

## HOW

### 统一接口与事件

新增播放前端接口，语义至少包括：

```text
start() / stop()
load(source) / play() / pause() / seek(position)
setVolume(volume)
showStandby(waiting) / showMenu(model)
status()

events: ready, position, ended, error, input, exit
```

`QueueManager` 仍是唯一播出状态源。前端不保存另一份频道或自行决定下一节目；它只执行当前状态并回报客观事件。服务器继续验证 `qid`，再执行连播、强切、异常记录和跳过。

### 可播放源解析

在队列条目和播放前端之间增加受信任的 `PlayableSourceResolver`：

- 本地条目：由片库 ID 解析为已登记绝对路径。Chrome 获得 `/media/:id/stream`，mpv 获得文件路径。
- 网站条目：缓存未就绪时保持等待；就绪后 Chrome 获得 `/cache/:key/stream`，mpv 获得 `CacheManager` 确认的缓存文件。
- 合集条目：先由现有合集解析器抽出实际一集，再按上述规则解析。
- 不允许 mpv IPC 直接加载遥控器提交的任意路径或 URL；所有来源必须先通过片库或缓存注册表。

### Chrome 前端

将现有 `BrowserController` + `/tv` + `/ws-tv` 适配为 `ChromeFrontend`，保留当前功能和调试流程。浏览器明确报编码/格式错误时，ADR-0011 的兼容缓存仍是 Chrome 的降级路径。

### mpv 前端

`MpvFrontend` 以类似以下的受控参数启动 mpv，具体参数在实现和真机测试中固化：

```text
--fullscreen --ontop --no-border --idle=yes --force-window=yes
--no-osc --cursor-autohide=always --hwdec=auto-safe
--input-ipc-server=\\.\pipe\showrunner-mpv
```

服务器用 JSON IPC 发送 `loadfile`、`seek`、`set_property pause/volume`等命令，订阅 `time-pos`、`duration`、`pause`、`eof-reached`和错误/进程退出。按键通过受控 `input.conf` 或项目自带 Lua 脚本转成 IPC `client-message`，仍由服务器的菜单模型处理上下、确认、菜单/返回；音量键保留给系统。待机、频道选择、点播列表和配对/恢复码使用 mpv OSD/Lua 渲染，不在 mpv 内建第二套业务状态。

mpv 优先直接解码原文件并使用硬件解码。不把 FFmpeg 实时推流作为主路径：若源编码不受硬件支持，“解码→重新编码→播放器再解码”仍会在弱性能电脑上卡顿。后续兼容链路按优先级考虑快速 remux、只转音频、硬件转码和后台预转码，最后才是软件全转码。

### 前端托管与模式

将单一浏览器托管推广为 `FrontendSupervisor`，继承 ADR-0007 的“任一时刻只托管一个播放实例”不变量：

- `normal`：只启动用户选择的 Chrome 或 mpv 播放前端。
- `maintenance`：先停止播放前端，再打开唯一受控的普通 Chrome 维护窗口；退出或超时后先关维护窗口，再恢复所选前端。
- `offline`：释放 mpv 和受控浏览器，不被看门狗重拉。

切换前端必须串行化为“停旧→确认退出→启新”。如新前端不存在或启动失败，遥控器和日志要显示可诊断错误；实现 `auto` 前不允许无提示回退。

### 配置与发布

遥控器设置页可查看前端状态并选择 `chrome`/`mpv`。更改是机器级操作，要持久化到 `config.json`，并在当次切换失败时恢复旧值。mpv 可先支持用户配置路径，再决定便携包是否内置固定来源的 Windows 二进制；打包、升级、授权和体积策略需在内置前单独核查。

### 可观测性与测试

状态 API 不暴露绝对媒体路径，但要报告前端类型、可执行文件是否找到、进程/IPC 是否存活、当前 `qid`、硬件解码状态和最近错误。测试通过注入假进程和假 IPC 验证：

- Chrome 的现有行为不变。
- 本地、网站缓存和合集条目解析为正确的前端源。
- mpv 只存在一个受控进程，意外退出可重拉。
- 切换、维护、下线和服务退出会回收旧进程与 IPC。
- 播放结束、卡住、解码失败和过期 `qid` 沿用服务器权威异常策略。
- 前端切换不修改频道、合集或播出时刻表资产。

## 备选方案

1. **完全用 mpv 替代 Chrome**：格式兼容性最佳，但会一次性丢失成熟电视 UI、调试路径和旧部署兼容，不选。
2. **继续只用 Chrome，所有失败都全转码**：实现简单，但对弱性能电脑的 CPU、延迟和缓存空间代价过高，不选。
3. **FFmpeg/VLC 实时转码推流给 Chrome**：可更快出首帧，但不会消除最昂贵的重新编码；一倍速度都达不到时会直接卡顿，还增加 seek、切台、子进程和分片回收复杂度，不作为主路径。
4. **只在安装前离线统一转码整个片库**：播放时稳定，但时间、空间和资产管理成本过高，且会修改或复制大量用户媒体，不选。

## 后果

- 弱性能电脑可用 mpv 直接播放更多容器和编码，减少转码和 Node HTTP 媒体中转。
- Chrome 前端保留，旧安装升级和调试不被迫迁移；用户可按机器能力选择。
- 播放前端切换是机器配置，不污染可分享的频道与合集资产。
- 需新增进程托管、Windows named pipe IPC、mpv 按键/OSD 层、源解析和机器级设置，实现与打包成本显著上升。
- mpv 提高兼容性但不能超过硬件解码能力；完全不受支持的编码仍可能需要 remux、部分转码、硬件转码或后台预转码。
- ADR-0011 不被废弃；它继续是 Chrome 前端及真正无法直放媒体的兼容降级方案。

## 实施顺序

1. 抽出播放前端契约和可播放源解析器，用 Chrome 适配器保证零行为变化。
2. 实现可注入测试的 mpv 进程/JSON IPC 控制器及看门狗。
3. 接入服务器播放状态、文件源解析、结束/进度/异常事件。
4. 实现 mpv 待机、频道/点播 OSD 和最小遥控器按键。
5. 统一维护/下线模式和单实例清理，再开放遥控器前端选择。
6. 完成 Windows 真机与 NAS 验收后，再决定便携包是否内置 mpv 及 `auto` 降级策略。
